# 07. 3단계 파이프라인 설계 및 CogniTrieve 구현 요약

## 전체 파이프라인

```
메타인지 기반 사전 진단 → 사용자 프롬프트 로그 입력 → 학습 확인 질문
```

시스템 설계 시 고려사항: (1) 자가진단은 본인의 결점을 측정하는 장치라는 점에서 답변
왜곡 가능성이 있어 이를 보완할 교차검증 단계가 필요, (2) 평가에 그치지 않고 개선
방향을 제시하는 단계가 필요.

---

## 1단계: 메타인지 기반 사전 진단

**목표**: 학습 과정 돌아보기·평가. 다차원(인지/행동/결과) 질문 트리로 학습자가 스스로
인지하는 AI 의존도와 학습 주체성을 측정. 결과는 방사형 차트(Radar Chart)로 시각화해
즉각적 자기 객관화 유도.

### 3차원 질문 프레임워크

1. **인지적 차원 (Cognitive)**: "스스로 생각(사고)했는가?" — AI 질문 전후 학생 두뇌의
   개입 정도
2. **행동적 차원 (Behavioral)**: "어떻게 상호작용했는가?" — 프롬프트 입력 방식·결과물
   활용 행태
3. **결과적 차원 (Result)**: "진짜 내 지식이 되었는가?" — 단기 제출용인지 장기 학습으로
   이어졌는지

### 설문 형식

- 응답 척도: 1(전혀 아니다) ~ 5(매우 그렇다), 리커트 척도형 채택 (확장성 고려)
- 각 시나리오당 5개 문항(학습 단계별 1개), 총점 5~25점

### 인지적 오류 페르소나 (4유형) 및 과락 로직

점수 구간을 4개 페르소나로 매핑하되, 총점이 높아도 핫스팟 문항에서 낮은 점수가 나오면
강등시키는 **'핫스팟 과락 방식'** 적용.

| 페르소나 | 특징 |
|---|---|
| 맹목적 의존형 | 글의 영혼(주제)부터 육체(문장)까지 전반을 AI에 대필. 인지적 구두쇠의 궁극적 형태 |
| 효율 중심형 | 직접 쓰는 수고는 감수하지만, 가장 어려운 '주제 도출'·'논리 검증'은 AI에 위임 |
| 방어형 | 스스로 뼈대·논리를 세우지만 결과물에 확신이 없어 AI 뒤에 목소리를 숨김 |
| 자기 주도형 | AI를 지적 스파링 파트너로 활용, 논리와 발표 주도권을 완벽히 통제 |

판별 로직 예시(CS 시나리오 기준):
```
If (총점 <= 11) OR (Q2 <= 2 AND Q4 <= 2): 맹목적 의존형
Else If (Q2 <= 2 OR Q4 <= 2): 효율 중심형
Else If (총점 <= 21) AND (Q5 <= 3): 방어형
Else: 자기 주도형
```
(Q2=시스템설계, Q4=디버깅 — 두 핫스팟 문항에 가중치)

## 2단계: 사용자 프롬프트 로그 입력 (교차 검증)

**목표**: 실제 학습 과정 수집, 프롬프트 작성 능력 평가(상하 연관성, 개수 등), AI 답변과
사용자 결과물의 관계(일치율, 본인 의견 함유·발전 여부) 평가. 1단계의 주관적 자가진단과
실제 행동 간의 간극 파악.

### 로그 수집 방법 검토

| 방법 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 수동 입력(복사-붙여넣기) | 개발 리소스 최소, API/권한 문제 없음 | 사용자 번거로움 | **채택** |
| 공식 데이터 내보내기(Export) | 대량 데이터 확보 | 실시간성 0, '즉각적 팝업' 목적과 불일치 | 미채택 |
| 브라우저 확장 프로그램 | UX 압도적 편리 | 서비스 UI 변경 시 유지보수 부담 큼(1인 개발 체제 부적합) | 미채택 |

### 프롬프트 로그 가공 항목

- 과제의 성질 이해(암기/자료조사/개념이해/개념적용실습/이해와논평)
- 질문 개수(양적) / 상하 질의응답 연관성(질적)
- AI 결과물에 대한 유저 피드백 사고 분석(비판적 수용 vs 무조건적 수용)
- **프롬프트 건전성 지수**: "해줘"/"짜줘" 등 수동적 지시어 페널티, "왜"/"어떻게" 등
  원리탐구형 단어 리워드 → 100점 만점 환산
- 위험 구간 하이라이팅: '인지적 구두쇠' 성향이 짙은 문장을 시각적으로 강조

## 3단계: 학습 확인 질문 (전이 검증)

**목표**: 지식의 실질적 내재화 여부 점검. 2단계 분석 결과의 취약점을 겨냥한 동적
서술형 질문 생성 → 의도적 인출 연습으로 바람직한 인지적 마찰을 시스템적으로 구현.

### 질문 포맷 검토

- **배제**: 예상 시험문제 작성(부담 큼), OX/객관식/빈칸채우기(메타인지 측면에서 인출이
  아닌 '친숙함의 오류' 유발 가능)
- **채택**: 함수 주석 작성, 에러 로그 원인 작성, 아이디어 근거 작성 — 부담은 낮으면서
  인출을 강제하는 1문장(50자 이내) 서술형

### 보상/시각화 로직

- 정답 키워드를 '해시태그 뱃지'로 누적, 대시보드에 전리품 형태로 표시
- 후보안: 육각형 레이더 차트(블룸 인지계층별 경험치), GitHub 잔디 UX 차용(메타인지
  인출 성공 캘린더)

## CogniTrieve 구현 요약 (1학기 최종 산출물)

- **프로젝트명 유래**: '인지(Cognitive)'+'인출(Retrieval)' 합성어, "인지적으로
  인출하라"는 의미
- **기술 스택**: Python 3.13, Streamlit, Google Generative AI API(gemini-3.1-flash-lite),
  Python unittest
- **배포**: https://cognitrieve.streamlit.app/ (Streamlit Community Cloud)
- **소스코드**: https://github.com/bugogi/CogniTrieve.git

### 구현 모듈

| 단계 | 파일 | 핵심 기능 |
|---|---|---|
| 1단계 | `1_사전진단.py`, `utils/logic_step1.py` | 5개 CS 학습행동 문항, 과락 로직 기반 4페르소나 판별 |
| 2단계 | `2_로그분석.py`, `utils/logic_step2.py` | Gemini API + JSON 모드로 Health Score/Risk Highlight/분석요약/3단계연동 CS개념 실시간 도출, 방어적 복구(Fallback) 설계 |
| 3단계 | `3_전이검증.py`, `utils/logic_step3.py` | 2단계 CS 개념 기반 1문장 서술형 퀴즈 동적 생성, 네이티브 문자열 매칭 채점(추가 AI 호출 비용 방지), 해시태그 뱃지 보상 UI |

### 품질 보증

- unittest + unittest.mock.patch로 1단계 과락 경계값(7개 케이스), 2단계 API 예외/폴백
  로직(3개 케이스) 자동화 테스트
- GitHub Flow 브랜치 전략, Streamlit Community Cloud 배포, 보안 시크릿 관리

### 확장 시 고려할 보정 사항 (1학기 결과보고서 메모)

1. 2·3단계 프롬프트 입출력값(JSON) 스키마 불일치 조정 필요
2. 3단계 질문 정답 산출법(AI 판단 기준) 정교화 필요
3. 3단계 보상 로직 — 현재는 점수보다 키워드 정답/오답 표시 위주로 단순화되어 있음
4. **동적 페르소나 조정(Dynamic Calibration)**: 1단계 주관적 진단과 2단계 로그 분석
   결과(health_score)를 비교해 "자기 주도형으로 나타났으나 실제 로그상 AI 의존도가
   높음" 같은 교차검증 피드백을 제공하면 교육용 플랫폼으로서 완성도가 높아질 것
5. 경고 메시지의 성장 지향적 리프레이밍: '맹목적 의존형' 같은 라벨은 유지하되, 임시적
   습관일 뿐이며 개선 가능하다는 성장 마인드셋 가이드를 추가 보완 권장

> **다음 확장에서 반영할 점**: 위 2·3단계 로직(Health Score, 프롬프트 건전성 지수 등)은
> 현재 '코드'라는 산출물에 최적화되어 있음. 유형 A/C/D 확장 시 이 분석 로직을 산출물
> 유형에 무관하게 통하는 형태로 일반화하는 작업이 `Phase 6`(로드맵 참조)의 핵심 과제.
