# 07. 3단계 파이프라인 설계 및 CogniTrieve 구현 요약

> **학습 유형 스코프**: 본 문서의 1단계(사전 진단) 유형별 문항·핫스팟 매핑과 2·3단계
> 일반화 로직은 학습 유형 '**과제(Assignment)**' 기준으로 설계되었다. '수강', '시험
> 대비' 학습 유형의 진단 문항은 각각 `08-1`, `08-2`를 참조 (전체 개요는 `08` 참조).
> 단, 파이프라인의 3단계 구조 자체와 4개 페르소나 정의·판별 공식은 학습 유형 공통으로
> 재사용된다.

> **상태**: 1단계(사전 진단)는 Phase 5, 2·3단계(로그 분석, 학습확인질문)는 Phase 6a/6b
> 에서 유형 A/B/C/D 전체로 일반화 완료 (설계 문서 범위, 코드 미변경). 이번 확장의

## 전체 파이프라인

```
메타인지 기반 사전 진단 → 사용자 프롬프트 로그 입력 → 학습 확인 질문
```

시스템 설계 시 고려사항: (1) 자가진단은 본인의 결점을 측정하는 장치라는 점에서 답변
왜곡 가능성이 있어 이를 보완할 교차검증 단계가 필요, (2) 평가에 그치지 않고 개선
방향을 제시하는 단계가 필요.

## 1단계: 메타인지 기반 사전 진단

**목표**: 학습 과정 돌아보기·평가. 다차원(인지/행동/결과) 질문 트리로 학습자가 스스로
인지하는 AI 의존도와 학습 주체성을 측정. 결과는 방사형 차트(Radar Chart)로 시각화해
즉각적 자기 객관화 유도.

### 3차원 질문 프레임워크

1. **인지적 차원 (Cognitive)**: "스스로 생각(사고)했는가?" — AI 질문 전후 학생 두뇌의
   개입 정도
2. **행동적 차원 (Behavioral)**: "어떻게 상호작용했는가?" — 프롬프트 입력 방식·결과물
   활용 행태
3. **결과적 차원 (Result)**: "진짜 내 지식이 되었는가?" — 단기 제출용인지 장기 학습으로
   이어졌는지

### 설문 형식

- 응답 척도: 1(전혀 아니다) ~ 5(매우 그렇다), 리커트 척도형 채택 (확장성 고려)
- 각 시나리오당 5개 문항(학습 단계별 1개), 총점 5~25점
- **문항 순서는 `04` 유형별 매트릭스의 Y축(학습 과정) 5단계 순서와 1:1 대응** — 즉
  Q1~Q5는 항상 "해당 유형의 1~5단계 학습 과정"을 가리키므로, 유형이 바뀌어도 문항
  번호의 구조적 의미(예: Q5=항상 마지막 성찰/회고 단계)는 고정된다.

### 버티컬별 문항 세트 관리 방식 (Phase 5)

**결정**: 문항 **텍스트**는 버티컬별로 분기하되, 채점·페르소나 판별 **로직**은 공통
파라미터로 관리한다 (완전 분기도, 완전 공통도 아닌 하이브리드).

- **분기하는 것**: 문항 문구 자체 — "수식화" 관련 질문과 "팀 토론" 관련 질문은 표현이
  다를 수밖에 없음
- **공통으로 유지하는 것**: (1) 5점 리커트 척도, (2) 문항 순서=학습 단계 순서, (3) 4개
  페르소나 명칭·판별 공식, (4) 핫스팟 과락 로직의 수식 구조
- **가변 파라미터화하는 것**: 어떤 문항 번호가 '핫스팟(최고위험)'인지 — 이 부분만
  유형마다 다르므로 아래처럼 룩업 테이블로 분리한다

```json
{
  "vertical": "C",
  "scenario": "물리 문제풀이",
  "questions": [
    "나는 문제에 어떤 물리 개념이 적용되는지 AI에 묻기 전에 스스로 떠올렸다.",
    "나는 문제 상황을 수식으로 세우는 과정을 스스로 수행했다.",
    "나는 계산 전개 과정을 AI가 준 결과를 그대로 베끼지 않고 직접 따라갔다.",
    "나는 최종 답이 물리적으로 타당한지 스스로 검증했다(단위, 극한상황 등).",
    "나는 내 풀이 과정의 약점이나 헷갈렸던 지점을 명확히 설명할 수 있다."
  ],
  "hotspot_primary": 2,
  "hotspot_secondary": 4,
  "hotspot_tier": { "primary": "최고위험", "secondary": "최고위험" }
}
```

`hotspot_tier`는 `09` 통합 검토에서 추가한 필드다 — A·B처럼 주/보조 문항의 위험
등급이 다른 유형(최고위험+위험)에서 과락 로직이 등급별로 다른 임계값을 적용할 수
있도록 한다 (아래 판별 로직 참조).

이렇게 구조화해두면 Phase 6(파이프라인 일반화)에서 유형 추가 시 로직 코드를 건드리지
않고 이 설정 객체만 늘리면 되는 구조가 된다.

### 유형별 문항 세트 및 핫스팟 매핑 (`04`/`06` 기반 확정)

| 유형 | Q1 | Q2 | Q3 | Q4 | Q5(고정: 성찰) |
|---|---|---|---|---|---|
| A. 에세이 | 텍스트 섭취·이해 | 관점 설정(개요) | **초안 집필(작문)** ⚠주 | 팀 토론·논리 통합 ⚠보조 | 발표 준비·성찰 |
| B. CS 코딩 | 요구사항 분석 | 시스템 설계 ⚠보조 | 코드 구현 | **디버깅 및 테스트** ⚠주 | 보고서·회고 |
| C. 물리 | 조건 파악·개념 상기 | **수식화** ⚠주 | 계산 및 전개 | **답 검증** ⚠주 | 풀이 서술·회고 |
| D. 디자인 | 리서치·레퍼런스 | **컨셉/아이디어 발상** ⚠주 | **시안 제작·시각화** ⚠주 | 기획 의도 서술 | 피드백 반영·회고 |

⚠주 = `05`/`06`에서 **최고위험**으로 명시된 핫스팟(과락 로직의 주 가중치),
⚠보조 = 그보다 낮은 '위험' 등급이지만 과락 로직에서 보조 가중치로 함께 쓰는 문항
(CS의 기존 Q2/Q4 방식을 그대로 일반화 규칙으로 채택). C·D는 최고위험이 두 곳이라
주·보조 모두 최고위험 등급이다.

### 인지적 오류 페르소나 (4유형, 도메인 무관 공통 정의) 및 일반화된 과락 로직

페르소나 명칭·판별 공식은 유형에 무관하게 공통 사용한다. 문항 텍스트만 바뀔 뿐, "핵심
인지 단계를 AI에 위임했는가"라는 판별 기준 자체는 산출물 유형과 무관하기 때문이다.

| 페르소나 | 특징 (도메인 무관 표현) |
|---|---|
| 맹목적 의존형 | 결과물의 뼈대(구조/논리)부터 표현(문장/코드/수식/시안)까지 전반을 AI에 위임. 인지적 구두쇠의 궁극적 형태 |
| 효율 중심형 | 직접 만드는 수고는 감수하지만, 가장 어려운 핵심 인지 단계(=핫스팟)는 AI에 위임 |
| 방어형 | 스스로 뼈대·논리를 세우지만 결과물에 확신이 없어 AI 뒤에 판단을 숨김 |
| 자기 주도형 | AI를 지적 스파링 파트너로 활용, 핵심 판단과 최종 주도권을 완벽히 통제 |

**일반화된 판별 로직** *(09 통합 검토 5.2 반영: 등급별 차등 임계값 적용)*:

기존에는 `HOTSPOT_PRIMARY`, `HOTSPOT_SECONDARY` 모두 동일 임계값(≤2)을 썼으나, A·B
유형처럼 "최고위험 1개 + 위험 1개" 조합에서는 위험 등급 문항이 최고위험 문항과 동일한
힘으로 페르소나를 강등시키는 문제가 있었다. `hotspot_tier`(4절 스키마) 정보를 실제로
활용해, 등급별로 임계값을 차등 적용한다.

```
설정: HOTSPOT_PRIMARY, HOTSPOT_SECONDARY = 위 매핑표에서 해당 유형의 ⚠주/⚠보조 문항 번호
      TIER_PRIMARY, TIER_SECONDARY = 각 문항의 위험 등급("최고위험" 또는 "위험")
      threshold(tier) = 2 if tier == "최고위험" else 1   # 위험 등급은 더 엄격한(낮은) 임계값
      REFLECTION = Q5 (모든 유형에서 고정)
      총점 = Q1 + Q2 + Q3 + Q4 + Q5

If (총점 <= 11) OR (Q[HOTSPOT_PRIMARY] <= threshold(TIER_PRIMARY) AND Q[HOTSPOT_SECONDARY] <= threshold(TIER_SECONDARY)):
    → 맹목적 의존형
Else If (Q[HOTSPOT_PRIMARY] <= threshold(TIER_PRIMARY) OR Q[HOTSPOT_SECONDARY] <= threshold(TIER_SECONDARY)):
    → 효율 중심형
Else If (총점 <= 21) AND (Q[REFLECTION] <= 3):
    → 방어형
Else:
    → 자기 주도형
```

**유형별 실제 임계값**: C·D·수강·시험대비(최고위험 2개)는 두 문항 모두 `threshold=2`로
기존과 동일하게 동작한다. A·B(최고위험 1개+위험 1개)만 변화가 생긴다 — 예를 들어
B(CS)는 `Q4(디버깅, 최고위험) <= 2`는 그대로지만, `Q2(시스템설계, 위험) <= 1`로
더 엄격해져, "시스템 설계를 다소 소홀히 했다(3점)" 정도로는 더 이상 효율 중심형으로
강등되지 않고 "거의 전혀 하지 않았다(1점)" 수준일 때만 반영된다.

예) 유형 C(물리)에 대입하면 `HOTSPOT_PRIMARY=Q2(수식화, 최고위험)`,
`HOTSPOT_SECONDARY=Q4(답검증, 최고위험)`가 되어, "수식화와 답 검증을 모두 AI에
맡겼다면 총점이 높아도 맹목적 의존형으로 강등"되는 구조가 기존과 동일하게 재현된다.

5. 나는 받은 피드백을 반영한 이유를 스스로 설명할 수 있다.

## 2단계: 사용자 프롬프트 로그 입력 (교차 검증)

**목표**: 실제 학습 과정 수집, 프롬프트 작성 능력 평가(상하 연관성, 개수 등), AI 답변과
사용자 결과물의 관계(일치율, 본인 의견 함유·발전 여부) 평가. 1단계의 주관적 자가진단과
실제 행동 간의 간극 파악.

### 로그 수집 방법 검토

| 방법 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 수동 입력(복사-붙여넣기) | 개발 리소스 최소, API/권한 문제 없음 | 사용자 번거로움 | **채택** |
| 공식 데이터 내보내기(Export) | 대량 데이터 확보 | 실시간성 0, '즉각적 팝업' 목적과 불일치 | 미채택 |
| 브라우저 확장 프로그램 | UX 압도적 편리 | 서비스 UI 변경 시 유지보수 부담 큼(1인 개발 체제 부적합) | 미채택 |

### 프롬프트 로그 가공 항목

- 과제의 성질 이해(암기/자료조사/개념이해/개념적용실습/이해와논평)
- 질문 개수(양적) / 상하 질의응답 연관성(질적)
- AI 결과물에 대한 유저 피드백 사고 분석(비판적 수용 vs 무조건적 수용)
- **프롬프트 건전성 지수**: "해줘"/"짜줘" 등 수동적 지시어 페널티, "왜"/"어떻게" 등
  원리탐구형 단어 리워드 → 100점 만점 환산
- 위험 구간 하이라이팅: '인지적 구두쇠' 성향이 짙은 문장을 시각적으로 강조

### 로그 분석 로직 일반화 (Phase 6a)

**문제 진단**: 위 5개 가공 항목 중 앞의 4개(과제 성질, 질문 개수·연관성, 피드백 사고
분석, 프롬프트 건전성 지수, 위험구간 하이라이팅)는 **프롬프트의 언어 패턴**만 분석하므로
이미 산출물 유형과 무관하게 동작한다. 일반화가 실제로 필요한 지점은 CogniTrieve 구현
모듈에만 존재하던 **"AI 답변과 사용자 결과물의 일치율/기여도" 비교 로직**이다 — 이건
산출물이 코드냐, 글이냐, 수식이냐, 이미지냐에 따라 애초에 "비교 가능한 형태"가 다르기
때문이다.

**유형별 결과물 비교 방식**

| 유형 | 비교 대상 | 비교 방식 | 비고 |
|---|---|---|---|
| A. 텍스트 | AI 초안 vs 사용자 최종 제출문 | 텍스트 임베딩 유사도(코사인 유사도) + 문장 재구성 비율 | 유사도 과도하게 높으면(예: >90%) 미수정 채택으로 판정 |
| B. 코드 | AI 생성 코드 vs 사용자 최종 코드 | 코드 diff / AST(추상구문트리) 유사도, 함수·변수명 일치율 | 1학기 기존 로직 |
| C. 수리 | AI 도출 수식·풀이 vs 사용자 서술 풀이 | 수식 구조 비교(기호연산 라이브러리로 동치 판정) + 전개 단계 수 비교 | 수식 자체보다 "전개 과정 생략 여부"가 핵심 |
| D. 디자인 | AI 생성 시안 vs 사용자 최종 시안 | 직접 비교 불가(생성형 이미지는 원본 개념이 없음) → **자기보고 방식으로 대체**: "그대로 채택/일부 수정/전면 재작업" 3지선다 + 수정 요청 프롬프트 횟수 | 이미지 유사도 비교보다 "AI 결과물에 몇 번 개입했는가"가 더 신뢰도 높은 대리 지표 |

**공통 산출 스키마 (Health Score)** *(09 통합 검토 5.4 반영: 균등 가중 + 보정 계획)*:
유형별 비교 방식은 다르지만, 최종 출력은 모두 0~100점의 정규화된 Health Score로
통일해 유형 간 비교·대시보드 시각화가 가능하도록 한다. 계산식은 세 요소를 **균등
가중(각 1/3)**한다:

```
Health Score = (프롬프트 건전성 지수 + 결과물 일치율 기반 자립도 점수 + 위험구간 감점) / 3
```

"결과물 일치율 기반 자립도 점수" 항목의 원천 데이터만 위 표의 유형별 방식으로
산출하고, 세 항목의 결합 비중은 유형에 무관하게 고정한다.

> **가중치 산정 근거**: 기존 0.4/0.4/0.2는 실증 데이터 없이 정한 값이라 그 자체가
> 근거 없는 정밀도였다. 세 요소 중 무엇이 더 중요한지 아직 알 수 없는 상태에서는
> 균등 가중이 "무정보 사전(no informative prior)"으로서 가장 정직한 기본값이다.
>
> **구현 시 유의**: 세 계수는 하드코딩하지 않고 `HEALTH_SCORE_WEIGHTS = [1/3, 1/3,
> 1/3]`처럼 명명된 상수로 분리한다.
>
> **보정 계획**: 파일럿 데이터 확보 후, Health Score 구성요소별 점수와 외부 타당도
> 기준(3단계 학습확인질문 정답률, 또는 지도교수·조교의 정성 평가) 간 상관관계를
> 분석해 계수를 재추정한다. 그 전까지는 균등 가중을 유지한다.

**개념/키워드 추출 일반화**: 기존 CS 로직은 "3단계연동 CS개념"을 실시간 추출했는데,
이를 "유형별 핫스팟 용어 사전" 참조 방식으로 일반화한다. `04` 매트릭스의 각 유형
Y축 단계명(예: C유형의 '수식화', D유형의 '컨셉 발상')을 프롬프트 템플릿에 미리 주입해
Gemini가 해당 유형 언어로 개념/키워드를 추출하도록 한다 — Phase 5의 JSON 설정 객체에
`concept_vocabulary` 필드를 추가하는 방식으로 구현 가능(설계 수준).

## 3단계: 학습 확인 질문 (전이 검증)

**목표**: 지식의 실질적 내재화 여부 점검. 2단계 분석 결과의 취약점을 겨냥한 동적
서술형 질문 생성 → 의도적 인출 연습으로 바람직한 인지적 마찰을 시스템적으로 구현.

### 질문 포맷 검토

- **배제**: 예상 시험문제 작성(부담 큼), OX/객관식/빈칸채우기(메타인지 측면에서 인출이
  아닌 '친숙함의 오류' 유발 가능)
- **채택**: 함수 주석 작성, 에러 로그 원인 작성, 아이디어 근거 작성 — 부담은 낮으면서
  인출을 강제하는 1문장(50자 이내) 서술형

### 질문 포맷 일반화 (Phase 6b)

기존 3개 포맷(함수 주석 작성, 에러 로그 원인 작성, 아이디어 근거 작성) 중 앞의 둘은
유형 B(CS) 전용, 마지막은 유형 D(디자인)에 그대로 재사용 가능하다. 유형 A(텍스트),
C(물리)에 대응하는 포맷이 없었으므로 `06`의 핫스팟 이벤트를 겨냥해 신규 포맷을 추가한다.
공통 원칙(배제/채택 기준, 50자 이내 서술형, 부담 최소화)은 유지한다.

| 유형 | 채택 포맷 | 질문 예시 | 대상 핫스팟 이벤트(`06`) |
|---|---|---|---|
| A. 텍스트 | **문단 핵심 논거 요약 작성** *(신규)* | "방금 쓴 문단의 핵심 주장을 나의 언어로 1문장 요약하세요" | `event_essay_full_generation` |
| B. 코드 | 함수 주석 작성 / 에러 로그 원인 작성 | "이 함수가 하는 일을 주석 한 줄로 작성하세요" / "이 에러가 왜 발생했는지 1문장으로 작성하세요" | `event_code_initial_generation` / `event_code_blind_debugging` |
| C. 물리 | **수식 도출 근거 작성** *(신규)* | "이 수식의 첫 번째 항이 어떤 물리 법칙에서 나왔는지 1문장으로 작성하세요" | `event_math_formulation_delegation` |
| D. 디자인 | 아이디어 근거 작성 | "이 컨셉을 선택한 이유를 1문장으로 작성하세요" | `event_design_concept_delegation` |

**채점 로직 일반화**: 기존 "네이티브 문자열 매칭 채점(추가 AI 호출 비용 방지)" 방식은
유형과 무관하게 유지 가능하다 — 단, 매칭 대상 키워드 뱅크를 유형별로 미리 정의해야
한다(예: C유형은 '뉴턴 제2법칙', '에너지 보존' 같은 물리 법칙 명칭, A유형은 문단의
핵심 명사구). Phase 6a의 `concept_vocabulary`를 채점 키워드 뱅크로 재사용하면 별도
설계 없이 3단계까지 일관되게 연결된다.

## CogniTrieve 구현 요약 (1학기 최종 산출물)

- **프로젝트명 유래**: '인지(Cognitive)'+'인출(Retrieval)' 합성어, "인지적으로
  인출하라"는 의미
- **기술 스택**: Python 3.13, Streamlit, Google Generative AI API(gemini-3.1-flash-lite),
  Python unittest
- **배포**: https://cognitrieve.streamlit.app/ (Streamlit Community Cloud)
- **소스코드**: https://github.com/bugogi/CogniTrieve.git

### 구현 모듈

| 단계 | 파일 | 핵심 기능 |
|---|---|---|
| 1단계 | `1_사전진단.py`, `utils/logic_step1.py` | 5개 CS 학습행동 문항, 과락 로직 기반 4페르소나 판별 |
| 2단계 | `2_로그분석.py`, `utils/logic_step2.py` | Gemini API + JSON 모드로 Health Score/Risk Highlight/분석요약/3단계연동 CS개념 실시간 도출, 방어적 복구(Fallback) 설계 |
| 3단계 | `3_전이검증.py`, `utils/logic_step3.py` | 2단계 CS 개념 기반 1문장 서술형 퀴즈 동적 생성, 네이티브 문자열 매칭 채점(추가 AI 호출 비용 방지), 해시태그 뱃지 보상 UI |

### 품질 보증

- unittest + unittest.mock.patch로 1단계 과락 경계값(7개 케이스), 2단계 API 예외/폴백
  로직(3개 케이스) 자동화 테스트
- GitHub Flow 브랜치 전략, Streamlit Community Cloud 배포, 보안 시크릿 관리

### 확장 시 고려할 보정 사항 (1학기 결과보고서 메모)

1. 2·3단계 프롬프트 입출력값(JSON) 스키마 불일치 조정 필요
2. 3단계 질문 정답 산출법(AI 판단 기준) 정교화 필요
3. 3단계 보상 로직 — 현재는 점수보다 키워드 정답/오답 표시 위주로 단순화되어 있음
4. **동적 페르소나 조정(Dynamic Calibration)**: 1단계 주관적 진단과 2단계 로그 분석
   결과(health_score)를 비교해 "자기 주도형으로 나타났으나 실제 로그상 AI 의존도가
   높음" 같은 교차검증 피드백을 제공하면 교육용 플랫폼으로서 완성도가 높아질 것
   — *(Phase 6a 반영)* 1단계 핫스팟 매핑(주/보조 문항)과 2단계 Health Score가 이제
   동일한 유형별 파라미터 테이블을 공유하므로, 두 단계 점수를 같은 축에서 직접 비교하는
   교차검증 로직 설계가 가능해짐. 실제 구현은 Phase 6 스코프(설계 문서까지) 밖이라
   추후 코드 반영 시 과제로 남겨둠.
5. 경고 메시지의 성장 지향적 리프레이밍: '맹목적 의존형' 같은 라벨은 유지하되, 임시적
   습관일 뿐이며 개선 가능하다는 성장 마인드셋 가이드를 추가 보완 권장

> **Phase 6 반영 완료**: 위 2·3단계 로직(Health Score, 프롬프트 건전성 지수, 학습확인
> 질문 포맷)을 산출물 유형(A/B/C/D)에 무관하게 통하는 형태로 일반화하는 설계를
> 완료했다 (`2단계: 사용자 프롬프트 로그 입력` 내 "로그 분석 로직 일반화(Phase 6a)",
> `3단계: 학습 확인 질문` 내 "질문 포맷 일반화(Phase 6b)" 참조). 코드
> (CogniTrieve `logic_step2.py`, `logic_step3.py`) 실제 리팩토링은 이번 확장 스코프에
> 포함하지 않으며, 다음 구현 세션에서 이 설계를 그대로 반영하면 된다.
