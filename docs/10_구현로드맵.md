# 10. 구현 로드맵 (CogniTrieve 확장)

> **상태**: 구현 착수 전 계획 수립 단계. 설계 로드맵(Phase 0~7.2, `02`~`09`)은 모두
> 완료되었고, 이 문서는 그 설계를 실제 코드(CogniTrieve)에 반영하는 **구현 로드맵**이다.
> 설계 Phase 번호와 혼동을 피하기 위해 구현 단계는 **"구현 Phase 1~5"**로 별도 번호를
> 매긴다.
> **전제**: Streamlit 유지 + Supabase(Postgres) 추가로 파일럿 데이터 축적, 학생 다수
> 대상 실제 파일럿을 목표로 한다 (이전 대화에서 결정).

## 구현 원칙

1. **한 번에 하나씩, 항상 실행 가능한 상태 유지**: 각 구현 Phase는 독립적으로 배포·시연
   가능해야 한다. Phase 중간에 앱이 완전히 망가진 상태로 며칠씩 두지 않는다.
2. **기존 아키텍처 원칙 계승**: `AI_INSTRUCTIONS.md`의 "로직은 `utils/`로 분리" 원칙을
   그대로 유지한다. 6개 케이스로 늘어나도 `pages/`는 UI만 담당한다.
3. **설계 문서가 곧 스펙**: 새로 짜는 코드가 아니라, `04`~`09`에 이미 있는 표·JSON
   스키마·수식을 그대로 옮기는 작업이 대부분이어야 한다. 새로운 설계 판단이 필요하면
   구현 중간에 멈추고 문서로 먼저 정리한다.
4. **Phase마다 브랜치 분리, 작은 PR**: `feature/impl-phase{N}-{요약}` 형식.

## 구현 Phase 1. 데이터 계층 및 설정 스키마 기반 다지기

**목표**: 아직 새로운 진단 로직은 만들지 않되, "6개 케이스를 다룰 수 있는 뼈대"와
"응답이 영구 저장되는 뼈대"를 먼저 완성한다. 이 Phase가 끝나면 기존 CS 진단은 그대로
작동하면서 데이터만 Supabase에 쌓이는 상태가 된다.

**작업 항목**
- [ ] Supabase 프로젝트 생성, `.env`/`.env.example`에 `SUPABASE_URL`, `SUPABASE_KEY` 추가
- [ ] DB 스키마 생성 (아래 "부록 A" 참조) — `cases`, `sessions`, `step1_responses`,
      `step2_responses`, `step3_responses` 5개 테이블
- [ ] `utils/db_handler.py` 신설 — Supabase 클라이언트 초기화, 세션 생성/조회, 응답
      저장 함수
- [ ] `cases` 테이블에 6개 케이스 시딩 — `07`/`08-1`/`08-2`의 JSON 스키마
      (`questions`, `hotspot_primary`, `hotspot_secondary`, `hotspot_tier`,
      `concept_vocabulary`)를 그대로 옮겨 심는 시딩 스크립트(`scripts/seed_cases.py`)
- [ ] 동의(consent) 화면 — `app.py` 진입 시 최초 1회, 수집 목적·활용 범위 안내 후 동의
      체크박스, 동의 시각 DB 저장
- [ ] 익명 식별자 발급 — 세션 시작 시 UUID 발급(`anon_id`), 학번 해시 입력 방식은
      선택 사항으로 남김(파일럿 운영 방식에 따라 Phase 5에서 결정)
- [ ] 기존 CS(`1_사전진단.py`) 결과가 `step1_responses`에 실제로 쌓이는지 확인

**완료 기준(Exit Criteria)**: 기존 CS 진단 플로우가 그대로 동작하면서, Supabase
대시보드에서 실제 응답 row가 쌓이는 것을 눈으로 확인할 수 있다.

## 구현 Phase 2. 1단계 사전진단 일반화 (6개 케이스 대응)

**목표**: `07`에서 설계한 일반화된 과락 로직(`threshold(tier)` 포함)을 실제로 구현하고,
학생이 케이스(산출물 유형 또는 학습 유형)를 선택해 해당 문항을 받는 흐름을 완성한다.

**작업 항목**
- [ ] `logic_step1.py` 리팩토링: `Q2`/`Q4` 하드코딩 제거 → `case_id`를 받아 `cases`
      테이블에서 `hotspot_primary`/`secondary`/`tier`를 조회하는 구조로 변경
- [ ] `threshold(tier)` 함수 구현 (`최고위험`→2, `위험`→1) — `07` 5.2 반영 로직 그대로
- [ ] `1_사전진단.py`에 케이스 선택 UI 추가 (예: "과제 - 에세이/코드/물리/디자인" vs
      "수강" vs "시험 대비" 라디오/셀렉트박스) — 선택된 `case_id`를 세션에 저장
- [ ] 선택된 케이스의 5문항을 동적으로 렌더링 (하드코딩된 CS 5문항 텍스트를 DB 조회로 대체)
- [ ] 페르소나 4종 설명 텍스트를 도메인 중립 표현(`07` 3절)으로 갱신
- [ ] `unittest` 확장: 6개 케이스 × 경계값 테스트 (기존 CS 7개 케이스 테스트를 템플릿으로
      나머지 5개 케이스에 동일 패턴 적용)
- [ ] Phase 1의 `step1_responses`에 `case_id` 포함해 저장되는지 확인

**완료 기준**: 6개 케이스 전부 진단 문항이 정상 렌더링되고, 각 케이스의 페르소나 판별이
`07`에 명시된 임계값대로 정확히 동작함을 테스트로 확인.

## 구현 Phase 3. 2단계 로그분석 일반화

**목표**: `07` Phase 6a에서 설계한 유형별 결과물 비교 로직과 균등 가중 Health Score를
구현한다. 이 Phase가 가장 큰 신규 개발이 필요한 구간이다 — 특히 텍스트/수식 비교
로직은 신규 라이브러리 도입이 필요하다.

**작업 항목**
- [ ] `HEALTH_SCORE_WEIGHTS = [1/3, 1/3, 1/3]` 상수 도입 (`07` 5.4 반영), 계산 함수
      `calculate_health_score()` 리팩토링
- [ ] 유형별 "결과물 일치율" 산출 로직 분기 (`utils/comparison/` 서브패키지 신설 권장):
  - B(코드): 기존 로직 유지
  - A(텍스트): 문장 임베딩 유사도 — `sentence-transformers` 또는 Gemini Embedding API
  - C(수리): 수식 구조 비교 — `sympy`로 동치 판정 + 전개 단계 수 비교
  - D(디자인): 자기보고 3지선다 + 수정요청 프롬프트 횟수 카운트 (UI 추가 필요)
  - 수강/시험대비: 산출물 없음 → 자기보고 방식 재사용(D와 유사한 패턴)
- [ ] `concept_vocabulary` 프롬프트 주입 — 기존 "CS 개념 추출"을 케이스별 용어사전
      기반으로 일반화 (`07` Phase 6a 참조)
- [ ] `2_로그분석.py` UI에 유형 D용 "채택 방식" 입력 위젯(3지선다) 추가
- [ ] `step2_responses` 저장 시 `case_id`, Health Score 세부 구성요소(추후 5.4 보정용
      원본값도 함께) 저장

**완료 기준**: 4개 산출물 유형 각각 로그를 입력했을 때 Health Score가 정상 산출되고,
수강/시험대비도 자기보고 방식으로 값이 산출된다.

## 부록 A. DB 스키마 초안 (Supabase/Postgres)

```sql
create table cases (
  case_id text primary key,           -- 'assignment_A' | 'assignment_B' | ... | 'course' | 'exam_prep'
  learning_type text not null,        -- '과제' | '수강' | '시험 대비'
  output_type text,                   -- 'A' | 'B' | 'C' | 'D' | null
  questions jsonb not null,           -- 5문항 배열
  hotspot_primary int not null,
  hotspot_secondary int not null,
  hotspot_tier jsonb not null,        -- {"primary": "최고위험", "secondary": "위험"}
  concept_vocabulary jsonb
);

create table sessions (
  session_id uuid primary key default gen_random_uuid(),
  anon_id text not null,              -- UUID 또는 해시된 식별자
  case_id text references cases(case_id),
  consented_at timestamptz,
  created_at timestamptz default now()
);

create table step1_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  q1 int, q2 int, q3 int, q4 int, q5 int,
  total_score int,
  persona text,
  created_at timestamptz default now()
);

create table step2_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  health_score numeric,
  prompt_soundness_score numeric,
  autonomy_score numeric,
  risk_deduction numeric,
  risk_highlight text,
  analysis_summary text,
  created_at timestamptz default now()
);

create table step3_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  quiz_type text,
  dynamic_question text,
  student_answer text,
  is_correct boolean,
  matched_keyword text,
  created_at timestamptz default now()
);
```

## 부록 B. 이번 로드맵에서 다루지 않는 것 (범위 밖)

- Health Score 가중치의 실증 재보정 (Phase 5 이후, 실제 파일럿 데이터 축적 후 별도 작업)
- 학습 유형 3종을 넘어서는 신규 확장 (설계 로드맵 Phase 7 이후 범위)
- 관리자 대시보드의 정교한 시각화(레이더 차트 등, `07` 3단계 "후보안"으로만 남아있던 것)
- 스택 자체의 변경(React/FastAPI 등) — 이전 대화에서 결정한 대로 이번 스코프에서 제외
