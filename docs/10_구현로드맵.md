# 10. 구현 로드맵 (CogniTrieve 확장)

> **상태**: 외부 세션(타 AI 모델)의 객관적 검토를 거쳐 1차 수정 완료. Phase 순서·스키마
> 유연성·`case_id` 버그·RLS·IRB·일정 추정·비용/보존정책 등 7개 지적 중 4개는 원안대로,
> 3개(RLS 심각도, Phase 3 브랜치 분리 여부, IRB 확신도)는 프로젝트 실정에 맞게 완화해
> 반영했다. 이후 **IRB·지도교수 관련 문구를 2차 정정**했다 — 검토·판단 과정은 대화
> 기록 참조.
>
> **프로젝트 소속 정정**: 이 프로젝트는 세종대 창의학기제(2026-1학기) 과목에서
> 출발했으나, **그 과목은 이미 종료되었다.** 지금(여름방학) 진행하는 확장은 학교
> 프로그램의 연장이 아니라 **개인 포트폴리오 목적의 개인 프로젝트**다. 문서 곳곳의
> "지도교수님"은 담당 교수님이 방학 중에도 개인적 선의로 도움을 주고 계신 관계를
> 뜻하며, 공식 보고·결재 절차가 아니다. IRB 등 공식 연구윤리 절차가 실제로 적용되는
> 대상인지도 이 문서는 단정하지 않는다.
>
> 설계 로드맵(Phase 0~7.2, `02`~`09`)은 모두 완료되었고, 이 문서는 그 설계를 실제
> 코드(CogniTrieve)에 반영하는 **구현 로드맵**이다. 설계 Phase 번호와 혼동을 피하기
> 위해 구현 단계는 **"구현 Phase 1~5"**로 별도 번호를 매긴다.
> **전제**: Streamlit 유지 + Supabase(Postgres) 추가로 파일럿 데이터 축적, 학생 다수
> 대상 실제 파일럿을 목표로 한다 (이전 대화에서 결정).

## 구현 원칙

1. **한 번에 하나씩, 항상 실행 가능한 상태 유지**: 각 구현 Phase는 독립적으로 배포·시연
   가능해야 한다. Phase 중간에 앱이 완전히 망가진 상태로 며칠씩 두지 않는다.
2. **기존 아키텍처 원칙 계승**: `AI_INSTRUCTIONS.md`의 "로직은 `utils/`로 분리" 원칙을
   그대로 유지한다. 6개 케이스로 늘어나도 `pages/`는 UI만 담당한다.
3. **설계 문서가 곧 스펙**: 새로 짜는 코드가 아니라, `04`~`09`에 이미 있는 표·JSON
   스키마·수식을 그대로 옮기는 작업이 대부분이어야 한다. 새로운 설계 판단이 필요하면
   구현 중간에 멈추고 문서로 먼저 정리한다.
4. **Phase마다 브랜치 분리, 작은 PR**: `feature/impl-phase{N}-{요약}` 형식.

## 부록 A. DB 스키마 초안 (Supabase/Postgres)

> **외부 검토 반영**: (1) 각 응답 테이블에 `case_id`를 직접 포함 — 세션 조인 없이
> 케이스별 집계가 가능하도록 수정(기존 초안은 `sessions` 조인이 필요해 작업 항목
> 문구와 불일치했음). (2) `step2_responses`의 세부 점수를 이름이 고정된 컬럼이 아니라
> `components jsonb`로 변경 — Phase 3에서 실제 비교 로직을 구현하며 항목명이 달라질
> 가능성이 높기 때문. (3) RLS 정책 예시 주석 추가.

```sql
create table cases (
  case_id text primary key,           -- 'assignment_A' | 'assignment_B' | ... | 'course' | 'exam_prep'
  learning_type text not null,        -- '과제' | '수강' | '시험 대비'
  output_type text,                   -- 'A' | 'B' | 'C' | 'D' | null
  questions jsonb not null,           -- 5문항 배열
  hotspot_primary int not null,
  hotspot_secondary int not null,
  hotspot_tier jsonb not null,        -- {"primary": "최고위험", "secondary": "위험"}
  concept_vocabulary jsonb
);

create table sessions (
  session_id uuid primary key default gen_random_uuid(),
  anon_id text not null,              -- UUID 또는 해시된 식별자
  case_id text references cases(case_id),
  consented_at timestamptz,
  created_at timestamptz default now()
);

create table step1_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함 (집계 편의)
  q1 int, q2 int, q3 int, q4 int, q5 int,
  total_score int,
  persona text,
  created_at timestamptz default now()
);

create table step2_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함
  health_score numeric,
  components jsonb,                          -- 유형별 세부 점수(항목명 유동적)
  risk_highlight text,
  analysis_summary text,
  created_at timestamptz default now()
);

create table step3_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함
  quiz_type text,
  dynamic_question text,
  student_answer text,
  is_correct boolean,
  matched_keyword text,
  created_at timestamptz default now()
);
```

## 부록 B. 일정 추정 원칙

- 각 Phase의 "예상 기간"은 정확한 예측이 아니라 **"이 기간을 넘기면 무엇을 줄일지
  판단하는 기준선"**이다.
- Phase 3(가장 불확실성이 큰 구간)에 버퍼를 몰아서 배정했다 — 나머지 Phase는 대부분
  기존 설계 문서를 코드로 옮기는 작업이라 상대적으로 예측 가능하다.
- 버퍼 소진 시 축소 기준은 각 Phase 항목에 개별적으로 명시한다(예: Phase 3의
  3-d 대체 경로 참조).

## 부록 C. 이번 로드맵에서 다루지 않는 것 (범위 밖)

- Health Score 가중치의 실증 재보정 (Phase 5 이후, 실제 파일럿 데이터 축적 후 별도 작업)
- 학습 유형 3종을 넘어서는 신규 확장 (설계 로드맵 Phase 7 이후 범위)
- 관리자 대시보드의 정교한 시각화(레이더 차트 등, `07` 3단계 "후보안"으로만 남아있던 것)
- 스택 자체의 변경(React/FastAPI 등) — 이전 대화에서 결정한 대로 이번 스코프에서 제외
