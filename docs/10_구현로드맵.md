# 10. 구현 로드맵 (CogniTrieve 확장)

> **상태**: 외부 세션(타 AI 모델)의 객관적 검토를 거쳐 1차 수정 완료. Phase 순서·스키마
> 유연성·`case_id` 버그·RLS·IRB·일정 추정·비용/보존정책 등 7개 지적 중 4개는 원안대로,
> 3개(RLS 심각도, Phase 3 브랜치 분리 여부, IRB 확신도)는 프로젝트 실정에 맞게 완화해
> 반영했다. 이후 **IRB·지도교수 관련 문구를 2차 정정**했다 — 검토·판단 과정은 대화
> 기록 참조.
>
> **프로젝트 소속 정정**: 이 프로젝트는 세종대 창의학기제(2026-1학기) 과목에서
> 출발했으나, **그 과목은 이미 종료되었다.** 지금(여름방학) 진행하는 확장은 학교
> 프로그램의 연장이 아니라 **개인 포트폴리오 목적의 개인 프로젝트**다. 문서 곳곳의
> "지도교수님"은 담당 교수님이 방학 중에도 개인적 선의로 도움을 주고 계신 관계를
> 뜻하며, 공식 보고·결재 절차가 아니다. IRB 등 공식 연구윤리 절차가 실제로 적용되는
> 대상인지도 이 문서는 단정하지 않는다.
>
> 설계 로드맵(Phase 0~7.2, `02`~`09`)은 모두 완료되었고, 이 문서는 그 설계를 실제
> 코드(CogniTrieve)에 반영하는 **구현 로드맵**이다. 설계 Phase 번호와 혼동을 피하기
> 위해 구현 단계는 **"구현 Phase 1~5"**로 별도 번호를 매긴다.
> **전제**: Streamlit 유지 + Supabase(Postgres) 추가로 파일럿 데이터 축적, 학생 다수
> 대상 실제 파일럿을 목표로 한다 (이전 대화에서 결정).

## 구현 원칙

1. **한 번에 하나씩, 항상 실행 가능한 상태 유지**: 각 구현 Phase는 독립적으로 배포·시연
   가능해야 한다. Phase 중간에 앱이 완전히 망가진 상태로 며칠씩 두지 않는다.
2. **기존 아키텍처 원칙 계승**: `AI_INSTRUCTIONS.md`의 "로직은 `utils/`로 분리" 원칙을
   그대로 유지한다. 6개 케이스로 늘어나도 `pages/`는 UI만 담당한다.
3. **설계 문서가 곧 스펙**: 새로 짜는 코드가 아니라, `04`~`09`에 이미 있는 표·JSON
   스키마·수식을 그대로 옮기는 작업이 대부분이어야 한다. 새로운 설계 판단이 필요하면
   구현 중간에 멈추고 문서로 먼저 정리한다.
4. **Phase마다 브랜치 분리, 작은 PR**: `feature/impl-phase{N}-{요약}` 형식.

## 구현 Phase 1. 데이터 계층 및 설정 스키마 기반 다지기

**목표**: 아직 새로운 진단 로직은 만들지 않되, "6개 케이스를 다룰 수 있는 뼈대"와
"응답이 영구 저장되는 뼈대"를 먼저 완성한다. 이 Phase가 끝나면 기존 CS 진단은 그대로
작동하면서 데이터만 Supabase에 쌓이는 상태가 된다.

**작업 항목**
- [ ] Supabase 프로젝트 생성 — **dev/prod 2개 분리** (Phase 개발 중 실수로 실제 데이터를
      건드리지 않기 위한 최소 롤백 장치)
- [ ] `.env`/`.env.example`에 `SUPABASE_URL`, `SUPABASE_KEY`(anon key) 추가. Streamlit은
      서버 사이드 실행 구조라 브라우저에 키가 노출될 경로는 없지만, 방어적 이중장치로
      최소 RLS 정책 1줄("service role만 쓰기, 세션 소유자만 자기 데이터 읽기") 설정
- [ ] DB 스키마 생성 (아래 "부록 A" 참조) — `cases`, `sessions`, `step1_responses`,
      `step2_responses`, `step3_responses` 5개 테이블. **`step1~3_responses`에
      `case_id`를 직접 포함**(세션 조인 없이 케이스별 집계 가능하도록)
- [ ] `step2_responses`의 세부 점수 컬럼은 이름을 미리 확정하지 않고 **`components
      jsonb`로 유연하게 설계** — Phase 3에서 실제 비교 로직을 구현해보기 전까지
      정확한 항목명이 불확실하기 때문. (아래 부록 A 갱신 참조)
- [ ] `utils/db_handler.py` 신설 — Supabase 클라이언트 초기화, 세션 생성/조회, 응답
      저장 함수
- [ ] `cases` 테이블에 6개 케이스 시딩 — `07`/`08-1`/`08-2`의 JSON 스키마
      (`questions`, `hotspot_primary`, `hotspot_secondary`, `hotspot_tier`,
      `concept_vocabulary`)를 그대로 옮겨 심는 시딩 스크립트(`scripts/seed_cases.py`)
- [ ] 동의(consent) 화면 — `app.py` 진입 시 최초 1회, 수집 목적·활용 범위·**보존 기간**
      안내 후 동의 체크박스, 동의 시각 DB 저장
- [ ] 익명 식별자 발급 — 세션 시작 시 UUID 발급(`anon_id`), 학번 해시 입력 방식은
      선택 사항으로 남김(파일럿 운영 방식에 따라 Phase 5에서 결정)
- [ ] **IRB(기관생명윤리위원회) 심의 필요 여부 확인** — 이 프로젝트는 창의학기제
      과목 종료 후 개인 포트폴리오 목적으로 진행되는 개인 프로젝트라, 학교의 공식
      연구윤리 절차(IRB)가 형식적으로 적용되는 대상인지 자체가 불확실하다. 세종대
      규정을 알지 못해 이 문서가 필요 여부를 단정하지 않으며, 원한다면 창의학기제를
      지도해주셨던 교수님께 (공식 보고 절차가 아닌, 개인적 조언을 구하는 형태로)
      여쭤봐도 좋다. 형식 요건과 무관하게, 실제 학생 데이터를 다루는 이상 동의·익명화
      절차(위 항목들)는 그대로 지킨다.
- [ ] 기존 CS(`1_사전진단.py`) 결과가 `step1_responses`에 실제로 쌓이는지 확인

**완료 기준(Exit Criteria)**: 기존 CS 진단 플로우가 그대로 동작하면서, Supabase
대시보드에서 실제 응답 row가 쌓이는 것을 눈으로 확인할 수 있다.

**예상 기간**: 1주 *(일정 추정에 대한 전반적 원칙은 "부록 B" 참조)*

## 구현 Phase 2. 1단계 사전진단 일반화 (6개 케이스 대응)

**목표**: `07`에서 설계한 일반화된 과락 로직(`threshold(tier)` 포함)을 실제로 구현하고,
학생이 케이스(산출물 유형 또는 학습 유형)를 선택해 해당 문항을 받는 흐름을 완성한다.

**작업 항목**
- [ ] `logic_step1.py` 리팩토링: `Q2`/`Q4` 하드코딩 제거 → `case_id`를 받아 `cases`
      테이블에서 `hotspot_primary`/`secondary`/`tier`를 조회하는 구조로 변경
- [ ] `threshold(tier)` 함수 구현 (`최고위험`→2, `위험`→1) — `07` 5.2 반영 로직 그대로
- [ ] `1_사전진단.py`에 케이스 선택 UI 추가 (예: "과제 - 에세이/코드/물리/디자인" vs
      "수강" vs "시험 대비" 라디오/셀렉트박스) — 선택된 `case_id`를 세션에 저장
- [ ] 선택된 케이스의 5문항을 동적으로 렌더링 (하드코딩된 CS 5문항 텍스트를 DB 조회로 대체)
- [ ] 페르소나 4종 설명 텍스트를 도메인 중립 표현(`07` 3절)으로 갱신
- [ ] `unittest` 확장: 6개 케이스 × 경계값 테스트 (기존 CS 7개 케이스 테스트를 템플릿으로
      나머지 5개 케이스에 동일 패턴 적용)
- [ ] Phase 1의 `step1_responses`에 `case_id` 포함해 저장되는지 확인

**완료 기준**: 6개 케이스 전부 진단 문항이 정상 렌더링되고, 각 케이스의 페르소나 판별이
`07`에 명시된 임계값대로 정확히 동작함을 테스트로 확인.

**예상 기간**: 1주

## 구현 Phase 3. 2단계 로그분석 일반화

**목표**: `07` Phase 6a에서 설계한 유형별 결과물 비교 로직과 균등 가중 Health Score를
구현한다. 이 Phase가 가장 큰 신규 개발이 필요한 구간이다 — 특히 텍스트/수식 비교
로직은 신규 라이브러리 도입이 필요하다.

> **외부 검토 반영**: 애초에 이 Phase 하나에 4개의 이질적 기술(코드 diff/텍스트
> 임베딩/수식 동치판정/자기보고)이 섞여 있어 "한 번에 하나씩" 원칙과 충돌한다는
> 지적을 받았다. 별도 브랜치로 쪼개지는 않되(1인 개발에서 PR 4개 관리 오버헤드가
> 더 크다고 판단), **작업 순서를 난이도가 낮은 것부터**로 재배치해 하나가 막혀도
> Phase 전체가 멈추지 않도록 한다.

**작업 항목 (난이도 순)**
- [ ] **3-a (가장 쉬움) 디자인/수강/시험대비 — 자기보고 방식**: "그대로 채택/일부
      수정/전면 재작업" 3지선다 UI + 수정요청 프롬프트 횟수 카운트. 외부 API·신규
      라이브러리 불필요, 가장 먼저 끝내 "성공 경험"을 확보하는 용도
- [ ] **3-b (기존 로직 확인) 코드(B)**: 기존 diff/AST 유사도 로직이 케이스 선택 구조에
      맞게 그대로 동작하는지 확인·리팩토링
- [ ] **3-c (중간 난이도) 텍스트(A) — 문장 임베딩 유사도**: `sentence-transformers`
      또는 Gemini Embedding API. **Streamlit Community Cloud 무료 티어 메모리 제약
      때문에 로컬 모델(sentence-transformers)보다 Gemini Embedding API 우선 검토**
      (인프라 부담을 서버가 아닌 API 호출로 넘기는 선택)
- [ ] **3-d (가장 어려움) 수리(C) — 수식 구조 비교**: `sympy`로 동치 판정 + 전개 단계
      수 비교. 학생이 자유 형식으로 입력한 수식 파싱이 예상대로 안 될 가능성이 가장
      높은 항목이므로 마지막에 배치, 파싱 실패 시 자기보고 방식(3-a)으로의 대체(fallback)
      경로를 함께 설계
- [ ] `HEALTH_SCORE_WEIGHTS = [1/3, 1/3, 1/3]` 상수 도입 (`07` 5.4 반영), 계산 함수
      `calculate_health_score()` 리팩토링
- [ ] `concept_vocabulary` 프롬프트 주입 — 기존 "CS 개념 추출"을 케이스별 용어사전
      기반으로 일반화 (`07` Phase 6a 참조)
- [ ] `step2_responses` 저장 시 `case_id`(직접 컬럼), Health Score 세부 구성요소를
      Phase 1에서 마련한 `components jsonb`에 저장 (추후 5.4 보정용 원본값 보존)

> ⚠ **측정 척도 재검토 필요** *(외부 검토로 재정의된 문제)*: 기존에 `07` 5.4는 이를
> "가중치가 검증 안 됨" 문제로만 다뤘으나, 더 근본적으로는 **케이스마다 측정 방법론
> 자체가 다른데(임베딩 유사도 vs sympy 동치판정 vs 자기보고 3지선다) 같은 0~100점
> 척도로 비교 가능하다고 가정해도 되는지**가 의문이라는 지적을 받았다. 이 항목의
> 구현 결과(3-a~3-d)를 실제로 비교해본 뒤, 파일럿 데이터 축적 전에 `07` 5.4를
> 재검토할지 여부를 Phase 3 완료 시점에 다시 판단한다.

**완료 기준**: 4개 산출물 유형 각각 로그를 입력했을 때 Health Score가 정상 산출되고,
수강/시험대비도 자기보고 방식으로 값이 산출된다.

**예상 기간**: 2~3주 (버퍼 포함). **버퍼 소진 기준**: 3주차에도 3-d(수식 비교)가
막혀 있으면, 수리 유형은 잠정적으로 3-a(자기보고) 방식으로 대체하고 Phase 4로
진행한다 — 정교한 수식 비교는 별도 후속 작업으로 미룬다.

## 구현 Phase 5. 파일럿 준비 및 배포

**목표**: 실제 학생 대상 파일럿을 시작할 수 있는 상태로 마무리한다.

**작업 항목**
- [ ] 익명 식별자 정책 최종 확정 (UUID만 쓸지, 학번 해시를 옵션으로 받을지 — 필요하면
      창의학기제 지도교수님께 개인적으로 여쭤보고 결정)
- [ ] **비용 한도 점검**: Gemini API 호출 비용(2·3단계), Gemini Embedding API 비용
      (Phase 3-c 채택 시), Supabase 무료 티어 한도(스토리지·요청 수)가 예상 파일럿
      규모(학급 단위, 수십 명)를 감당하는지 대략 계산
- [ ] **데이터 보존·파기 정책 확정**: 수집 목적 달성 후 파기 시점(예: "파일럿 종료 후
      N개월"), 파기 방법을 동의 화면 문구에 반영

## 부록 A. DB 스키마 초안 (Supabase/Postgres)

> **외부 검토 반영**: (1) 각 응답 테이블에 `case_id`를 직접 포함 — 세션 조인 없이
> 케이스별 집계가 가능하도록 수정(기존 초안은 `sessions` 조인이 필요해 작업 항목
> 문구와 불일치했음). (2) `step2_responses`의 세부 점수를 이름이 고정된 컬럼이 아니라
> `components jsonb`로 변경 — Phase 3에서 실제 비교 로직을 구현하며 항목명이 달라질
> 가능성이 높기 때문. (3) RLS 정책 예시 주석 추가.

```sql
create table cases (
  case_id text primary key,           -- 'assignment_A' | 'assignment_B' | ... | 'course' | 'exam_prep'
  learning_type text not null,        -- '과제' | '수강' | '시험 대비'
  output_type text,                   -- 'A' | 'B' | 'C' | 'D' | null
  questions jsonb not null,           -- 5문항 배열
  hotspot_primary int not null,
  hotspot_secondary int not null,
  hotspot_tier jsonb not null,        -- {"primary": "최고위험", "secondary": "위험"}
  concept_vocabulary jsonb
);

create table sessions (
  session_id uuid primary key default gen_random_uuid(),
  anon_id text not null,              -- UUID 또는 해시된 식별자
  case_id text references cases(case_id),
  consented_at timestamptz,
  created_at timestamptz default now()
);

create table step1_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함 (집계 편의)
  q1 int, q2 int, q3 int, q4 int, q5 int,
  total_score int,
  persona text,
  created_at timestamptz default now()
);

create table step2_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함
  health_score numeric,
  components jsonb,                          -- 유형별 세부 점수(항목명 유동적)
  risk_highlight text,
  analysis_summary text,
  created_at timestamptz default now()
);

create table step3_responses (
  id bigint generated always as identity primary key,
  session_id uuid references sessions(session_id),
  case_id text references cases(case_id),   -- 직접 포함
  quiz_type text,
  dynamic_question text,
  student_answer text,
  is_correct boolean,
  matched_keyword text,
  created_at timestamptz default now()
);
```

## 부록 B. 일정 추정 원칙

- 각 Phase의 "예상 기간"은 정확한 예측이 아니라 **"이 기간을 넘기면 무엇을 줄일지
  판단하는 기준선"**이다.
- Phase 3(가장 불확실성이 큰 구간)에 버퍼를 몰아서 배정했다 — 나머지 Phase는 대부분
  기존 설계 문서를 코드로 옮기는 작업이라 상대적으로 예측 가능하다.
- 버퍼 소진 시 축소 기준은 각 Phase 항목에 개별적으로 명시한다(예: Phase 3의
  3-d 대체 경로 참조).
