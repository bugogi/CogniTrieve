# 09. 학습 유형 통합 비교 및 설계 정합성 검토

> **상태**: Phase 0~7.2 설계 완료 후 통합 검토 단계에서 작성. `08`(축 설계),
> `08-1`(수강), `08-2`(시험 대비) 및 `02`~`07`(과제)의 개별 설계를 하나의 표로
> 통합하고, 전체 설계에서 발견된 정합성 이슈를 정리한다.
> **목적**: 구현(코드) 착수 전 설계를 한 번 더 다지기 위한 문서 — 신규 설계 내용은
> 없으며, 기존 문서(`02`~`08-2`)를 재정리·재검토한 것이다.

## 1. 학습 유형 3종 개요

| 학습 유형 | 목표 | 산출물 유형 구분 | Y축 프로세스 | 대표 문서 |
|---|---|---|---|---|
| 과제 (Assignment) | 제출용 산출물 완성 | 4종(A/B/C/D) 필요 | 유형별 상이(5단계) | `02`~`07` |
| 수강 (Course Engagement) | 강의 내용 내재화 | 불필요(공통 1종) | 예습→필기→질의→복습→자기점검 | `08-1` |
| 시험 대비 (Exam Prep) | 실전 인출 능력 확보 | 불필요(공통 1종) | 범위파악→개념정리→모의풀이→오답분석→최종점검 | `08-2` |

## 2. 케이스별 핫스팟·이벤트·진단 통합표

과제는 산출물 유형(A/B/C/D)별로 갈라지므로, 사실상 총 6개 케이스(과제-A, 과제-B,
과제-C, 과제-D, 수강, 시험대비)가 이 프로젝트의 설계 단위다.

| 케이스 | 최고위험 학습단계 | 이벤트 유형 분포 | 진단 핫스팟 문항 | X축 최상위 인지 라벨 |
|---|---|---|---|---|
| 과제-A(에세이) | 초안 집필(작문) | 3×1 | Q3 | 창조&주제서술 |
| 과제-B(CS) | 디버깅 및 테스트 | 3×1, 4×1, 5×1 | Q4(주) / Q2(보조, 위험등급) | 창조&아키텍처 |
| 과제-C(물리) | 수식화 / 답 검증 | 3×2, 4×1 | Q2 / Q4 | 창조&대안풀이법 |
| 과제-D(디자인) | 컨셉발상 / 시안제작 | 3×2, 5×1 | Q2 / Q3 | 창조&정당화서술 |
| 수강 | 필기 / 복습정리 | 3×2, 4×1 | Q2 / Q4 | 재구성&자기설명 |
| 시험 대비 | 모의풀이 / 오답분석 | 3×2, 4×1 | Q3 / Q4 | 재구성&자기설명 |

**관찰**: 수강·시험대비는 이벤트 유형 분포(3×2, 4×1)가 과제-C·D와 동일한 패턴을
보인다 — 이는 "최고위험 2곳"을 가진 케이스가 공통적으로 "생성형 위임 2건 + 검토형
위임 1건" 구조를 갖는다는 뜻으로 해석할 수 있다. 반면 과제-A·B는 최고위험이 1곳뿐이라
이 패턴에서 벗어난다.

## 3. 이벤트 유형(택소노미) 전체 분포

`06`에서 정의한 5개 이벤트 유형이 6개 케이스에 걸쳐 어떻게 분포하는지 집계했다.

| 이벤트 유형 | 과제-A | 과제-B | 과제-C | 과제-D | 수강 | 시험대비 | 합계 |
|---|---|---|---|---|---|---|---|
| 1. 정보탐색 | - | - | - | - | - | - | 0 (미등록) |
| 2. 이해증강 | - | - | - | - | - | - | 0 (미등록) |
| 3. 결과물 생성 | 1 | 1 | 2 | 2 | 2 | 2 | 10 |
| 4. 문제해결및검토 | - | 1 | 1 | - | 1 | 1 | 4 |
| 5. 사후 합리화 | - | 1 | - | 1 | - | - | 2 |

**관찰**: 유형 5(사후 합리화)는 과제-B, 과제-D에만 존재하고 수강·시험대비에는 없다.
`08-2`에서 이미 지적했듯 "제출용 산출물이 없는 학습 유형에는 사후 정당화할 대상 자체가
없다"는 가설과 일치한다. 유형 1·2는 전 케이스에 걸쳐 단 하나도 정식 이벤트로 등록되지
않았다 — Level 1·2 개입은 상대적으로 안전하다고 판단해 의도적으로 제외한 결과다(`06`
참조).

## 4. 진단 파이프라인 공통 스키마 (최종 통합본)

```json
{
  "case_id": "vertical_C | vertical_D | course_engagement | exam_prep 등",
  "learning_type": "과제 | 수강 | 시험 대비",
  "output_type": "A | B | C | D | null (수강·시험대비는 null)",
  "questions": ["문항1", "문항2", "문항3", "문항4", "문항5"],
  "hotspot_primary": 2,
  "hotspot_secondary": 4,
  "hotspot_tier": { "primary": "최고위험", "secondary": "최고위험 | 위험" },
  "concept_vocabulary": ["케이스별 핫스팟 용어 사전 — Phase 6a 참조"]
}
```

`hotspot_tier` 필드는 이번 통합 검토 과정에서 새로 추가한 필드다 — 기존 스키마
(Phase 5)에는 없었으나, 아래 5.2 항목의 문제(주/보조 문항의 등급 차이가 채점 로직에
반영되지 않는 문제)를 추후 보완하려면 최소한 등급 정보 자체는 스키마에 남아 있어야
하기 때문이다. 실제 가중치 반영 로직은 이번 스코프에서 구현하지 않는다.

## 5. 설계 정합성 검토 메모

구현 착수 전 재점검하며 발견한 사항이다. 1·3번은 이번에 함께 반영했고, 2·4·5번은
판단이 필요해 메모로 남긴다.

### 5.1 위험도 3단계 → 진단 로직 2단계 단순화 (반영 보류)
`05`는 [주의]/[위험]/[최고위험] 3단계로 학습단계를 구분했으나, Phase 5의 과락 로직은
`Q_primary`/`Q_secondary` 2개 문항만 가중치를 갖고 나머지는 총점에만 반영된다. "주의"
등급 단계의 저조한 응답이 페르소나 판정에 전혀 영향을 주지 않는 셈이다. 위 4절 스키마에
`hotspot_tier` 필드를 추가해 정보 자체는 보존해뒀으나, 채점 공식에 3단계 가중치를
반영할지는 구현 단계에서 결정할 문제로 남겨둔다.

### 5.2 비대칭 핫스팟 쌍의 동일 가중치 — ✅ 채택 완료
과제-A·B는 "최고위험 1개+위험 1개" 조합이고 과제-C·D·수강·시험대비는 "최고위험 2개"
조합인데, 과락 공식이 두 경우를 동일하게 취급하던 문제. **등급별 임계값 차등**(최고
위험 `<=2`, 위험 `<=1`) 방식으로 채택해 `07`의 판별 로직에 반영했다. 4절 스키마에
이미 있던 `hotspot_tier` 필드를 실제로 활용하는 구조라 구현 비용이 낮고, `05`가 이미
내려둔 등급 판단을 그대로 존중한다는 점에서 새로운 임의 계수를 만들지 않는다는 장점이
있다. C·D·수강·시험대비(최고위험 2개)는 임계값이 기존과 동일해 영향이 없다.

### 5.3 이벤트 번호 체계 불연속 (문서화로 해결)
`06`의 이벤트는 1~4번까지 사용했는데 `08-1`/`08-2`는 이어서 5·6번이 아닌 8·9번을
사용했다(문서 번호를 이벤트 번호에 그대로 반영한 결과). 전체 이벤트 목록에 5·6·7번이
없어 혼란을 줄 수 있다. **번호를 다시 매기지는 않되**(기존 문서 참조 관계가 깨질 위험),
아래처럼 전체 이벤트 색인표를 만들어 불연속을 명시적으로 안내한다.

| 이벤트 번호 | 케이스 | 문서 |
|---|---|---|
| 1 | 과제-A | `06` |
| 2-1~2-3 | 과제-B | `06` |
| 3-1~3-3 | 과제-C | `06` |
| 4-1~4-3 | 과제-D | `06` |
| *(5~7 결번 — 문서 번호 05~07은 매트릭스/파이프라인 문서에 이미 사용되어 이벤트 번호로 재사용하지 않음)* | | |
| 8-1~8-3 | 수강 | `08-1` |
| 9-1~9-3 | 시험 대비 | `08-2` |

### 5.4 Health Score 가중합 계수의 근거 부재 — ✅ 채택 완료
Phase 6a에서 정한 `(건전성지수×0.4)+(자립도점수×0.4)+(위험구간감점×0.2)`는 실증 근거
없는 1차 가설이었다. **균등 가중(각 1/3) + 보정 계획 수립**으로 채택해 `07`에
반영했다. 근거 없는 소수점 가중치보다 균등 가중이 "무정보 사전"으로서 더 정직하며,
계수는 하드코딩하지 않고 명명된 상수로 분리해 파일럿 데이터 확보 후(3단계 정답률 또는
지도교수·조교 평가와의 상관관계 분석으로) 재추정하는 절차를 `07`에 명시했다.

### 5.5 유형 B(CS) 진단 문항 실제 텍스트 부재 — ✅ 반영 완료
A/C/D는 5문항 예시가 `07`에 직접 적혀 있으나 B(CS)는 생략되어 있던 문제. 프로젝트
담당자가 1학기 CogniTrieve `1_사전진단.py` 원본을 직접 제공해 `07`에 그대로 옮겨
적었다. 부수적으로, 원본 코드의 `★ 핵심 설계 역량`(Q2)·`★ 핵심 디버깅 역량`(Q4)
표시가 `07`의 기존 매핑(Q2=⚠보조, Q4=⚠주)과 정확히 일치함을 확인했다 — 이번
세션에서 A/C/D 문항을 만들 때 참고한 "★ 표시로 핫스팟을 명시하는" 방식이 실제로
1학기 원본 설계에서 유래한 것이었다는 점도 함께 기록해둔다.
